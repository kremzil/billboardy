# Backend

Backend реализован как WordPress plugin в каталоге `billboardy-map-api/`.

## Задача backend-части

- хранить или читать данные рекламных плоскостей;
- нормализовать их;
- отдавать стабильный REST API для frontend-карты;
- предоставлять административные инструменты для настроек и импорта.

## Основные зоны кода

### Entry / bootstrap

- `billboardy-map-api/billboardy-map-api.php`
- `billboardy-map-api/src/Plugin.php`

Тут регистрируются хуки, поднимаются зависимости и подключаются REST/admin части.

### Admin

- `billboardy-map-api/src/Admin/SettingsPage.php`
- `billboardy-map-api/src/Admin/ImportPage.php`
- `billboardy-map-api/src/Admin/InquiryLogPage.php`

Тут лежат:

- настройки плагина;
- очистка и прогрев кэша;
- интерфейс импорта файлов.
- закрытый журнал заявок с поиском, фильтрами и CSV-экспортом.

### Database

- `billboardy-map-api/src/Database/Schema.php`

Тут описана собственная таблица и её создание/обновление.

### Import

- `billboardy-map-api/src/Import/AdSpaceImporter.php`

Тут живёт разбор файлов, нормализация входных строк и запись в таблицу.

### Repository

- `billboardy-map-api/src/Repository/`

Эта зона отвечает за доступ к данным:

- чтение из собственной таблицы;
- fallback на WooCommerce;
- переключение между источниками.

### Domain

- `billboardy-map-api/src/Domain/AdSpaceMapper.php`

Тут сосредоточены правила нормализации и подготовки доменной модели.

### Service

- `billboardy-map-api/src/Service/AdSpaceService.php`

Тут лежит логика:

- фильтрации;
- кэширования;
- SQL-backed pagination для `/ad-spaces`, когда runtime-источником служит собственная таблица;
- облегчённого `map-points` payload без дублирующего `data`;
- server-side cluster preparation;
- выдачи одной точки и SQL-backed фильтров.

### REST

- `billboardy-map-api/src/Rest/AdSpaceApiController.php`

Тут объявлены endpoints и response headers.

## Практические команды

```powershell
Get-ChildItem -Path billboardy-map-api -Recurse -Filter *.php | ForEach-Object { php -l $_.FullName }
```

## Когда идти в backend

Идите в backend, если нужно:

- изменить контракт API;
- ускорить SQL или кэш;
- добавить/изменить импорт;
- менять источник runtime-данных;
- добавить настройки WordPress.

## Текущие performance-заметки

- `/map-points` при работе с собственной таблицей использует отдельную SQL-проекцию только под поля карты и списка, без полной доменной модели.
- `/ad-spaces` при работе с собственной таблицей использует SQL `COUNT(*)` и `LIMIT/OFFSET`, а не пагинацию поверх полного массива в PHP.
- `/ad-spaces` принимает те же `bounds`, `media_type`, `city` и `search`, что и карта, поэтому frontend может лениво подгружать список объектов текущей области по 10 записей без запроса полного набора.
- `/inquiries` принимает публичный POST из dopyt-виджета frontend. Перед валидацией контактных полей endpoint проверяет одноразовый Cloudflare Turnstile token и его `action`; запрос без успешной серверной проверки завершается с HTTP 403 и не вызывает `wp_mail`. Secret задаётся только на сервере константой `BILLBOARDY_TURNSTILE_SECRET` в `wp-config.php`, а публичный site key — frontend-переменной `PUBLIC_TURNSTILE_SITE_KEY`. После anti-spam проверки endpoint валидирует контактные поля и выбранные плоскости; для старой клиентской записи с пустым названием плоскости восстанавливает его из кода, адреса или ID. Затем заявка сохраняется в таблице `wp_billboardy_inquiry_logs`, письмо отправляется через `wp_mail`, а журнал фиксирует статус `sent` или `failed`. Honeypot/CAPTCHA-спам и невалидные формы не записываются. Журнал доступен только администраторам в `Settings → Dopyty Billboardy`, поддерживает поиск, фильтры и CSV; записи автоматически удаляются через 180 дней. Адрес письма берётся из настройки плагина `E-mail pre dopyty`; если настройка пустая или невалидная, используется admin email сайта.
- `/filters` при работе с собственной таблицей строятся через `SELECT DISTINCT`, а не через проход по `allMapped()`.
- Если собственная таблица пуста и backend падает в WooCommerce fallback, путь остаётся заметно тяжелее, чем чтение из dedicated table.

## Защита заявок от повторов и частых отправок

С 2026-09-29 `InquirySubmissionGuard` защищает общий `/inquiries` для `contact`, `quick` и `map` после проверки Turnstile и обязательных полей:

- между разными заявками одного email — минимум 60 секунд;
- максимум 5 попыток отправки с email за скользящий час;
- максимум 20 попыток с публичного `REMOTE_ADDR` за скользящие 10 минут;
- одинаковая заявка, уже отправленная за последние 15 минут, получает прежний успешный ответ `200` с `data.duplicate=true`, без нового письма или записи;
- одинаковая заявка в состоянии `pending` получает `409`, превышение лимита — `429`; ошибки содержат `retry_after` в секундах. Существующий frontend сохраняет заполненные данные и показывает сообщение с предложением повторить позже.

Лимиты общие для всех трёх источников. Email приводится к нижнему регистру. Отпечаток включает очищенные значимые поля и параметры заявки, а для карты — отсортированные ID выбранных плоскостей; токен CAPTCHA и IP не влияют на дедупликацию. IP хранится только в виде HMAC, исходный адрес не записывается. Заголовки `X-Forwarded-For` и аналогичные не используются: приватный, зарезервированный или неизвестный `REMOTE_ADDR` пропускает только IP-лимит, сохраняя ограничения email и дублей. Для публичного прокси необходима отдельная проверенная настройка определения адреса клиента.

Авторитетное состояние находится в существующем журнале заявок. Миграция схемы `1.2.0` добавляет `request_hash`, `ip_hash` и составные индексы. Короткая секция проверки и создания `pending` сериализована через MySQL/MariaDB `GET_LOCK`; Turnstile и SMTP выполняются вне блокировки. При недоступности блокировки или хранилища endpoint отвечает `503` и не отправляет письмо. Подтверждённый `wp_mail=false` переводит строку в `failed`, разрешая немедленный повтор, но не отменяет часовой/IP счётчик попыток. Если процесс аварийно завершится после SMTP до `markSent`, `pending` подавляет повтор 15 минут; гарантии exactly-once между SMTP и БД нет. Старые записи не получают отпечатки задним числом. Очистка остаётся общей: 180 дней.

Интеграционная проверка на WordPress/MySQL:

```sh
/home/wp-cli.phar eval-file /path/to/billboardy-map-api/tests/InquiryProtectionIntegrationTest.php --skip-plugins --skip-themes
```

Тест создаёт и удаляет только собственные таблицы со случайным префиксом `bbtest_*`, не меняет рабочую версию схемы и проверяет неизменность количества рабочих заявок. Проверяются реальные SQL-операции и конкурентные процессы, а ответы Cloudflare и `wp_mail` заменяются заглушками: тест не отправляет письма и не доказывает доставку через SMTP.

Проверено и установлено 2026-09-29: 59 интеграционных проверок на MariaDB 11.4.13 / PHP 8.5.10 прошли, включая конкурентные дубли и достижение IP-лимита. На временной консоли с 256 MiB памяти тест использует два дочерних процесса; запуск шести исчерпал память, оставшиеся таблицы того запуска были отдельно проверены и удалены. Рабочие заявки не изменялись (35 записей до и после). Публичная контактная страница вернула `200`, API без Turnstile — `403`; рабочая версия схемы подтверждена как `1.2.0`. Временный HTTP-пробник подтвердил, что PHP `REMOTE_ADDR` совпадает с публичным адресом клиента в access log; пробник удалён. Исходные PHP-файлы, схема таблицы и SHA-256 manifest сохранены на сервере в `~/billboardy.sk/_backups/20260929-inquiry-protection/`.
