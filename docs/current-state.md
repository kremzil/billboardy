# Текущее состояние

Дата снимка: 2026-04-23

## Общая картина

Проект разделён на две части:

- WordPress plugin как backend/API слой
- Astro приложение как отдельный frontend карты

В репозитории уже есть рабочий MVP интерактивной карты с импортом данных в собственную таблицу WordPress.

## Что уже реализовано

### Backend

- Есть отдельный WordPress plugin `billboardy-map-api`.
- Есть собственная таблица для нормализованных рекламных плоскостей.
- Есть импорт данных через админку WordPress.
- Есть REST API для карты, списка объектов, одной точки и фильтров.
- Есть fallback-логика и кэширование.
- `/map-points` использует отдельную облегчённую SQL-выборку по bounds для собственной таблицы.
- `/ad-spaces` использует SQL `COUNT(*)` и `LIMIT/OFFSET`, если runtime-источником служит собственная таблица.
- `/filters` используют SQL `DISTINCT`, если runtime-источником служит собственная таблица.
- Для карты добавлены:
  - snap-to-grid нормализация bounds для cache keys
  - transient caching
  - HTTP `Cache-Control` для `/map-points` и `/filters`
  - server-side clustering fallback при слишком большом числе raw points

### Frontend

- Есть отдельный Astro проект с Tailwind.
- Карта работает через Google Maps JavaScript API.
- Есть фильтры, список объектов в текущей области, popup карточка и CTA.
- Есть кластеризация и отдельная обработка групп объектов на одинаковых координатах.
- Есть клиентский cache payload'ов карты.
- Добавлено diff-обновление маркеров, чтобы не делать полный teardown/rebuild на каждый `idle`.
- Добавлена отмена устаревших `/map-points` запросов при активном pan/zoom/search.

## Что считать текущим runtime-источником данных

Приоритетный источник на текущий момент:

1. собственная таблица WordPress, если в неё импортированы данные;
2. fallback на WooCommerce, если таблица пуста.

То есть проект уже умеет жить не только поверх WooCommerce.

## Текущие сильные стороны

- Backend и frontend разделены.
- Есть импорт в собственную таблицу.
- Есть базовая оптимизация для больших наборов точек и горячих API-path'ов карты.
- Есть отдельный build frontend для выкладки на сервер.

## Известные ограничения и незакрытые темы

- Нет полноценного набора автоматических тестов.
- Нет отдельного документа с формализованным deployment flow.
- Нет отдельного documented workflow для обновления данных по расписанию.
- WooCommerce fallback остаётся более тяжёлым путём, чем работа через собственную таблицу.
- Street View fallback для точек без фото пока не реализован.

## Что обновлять в этом файле

Имеет смысл обновлять этот документ, когда меняется одно из следующего:

- источник runtime-данных
- схема хранения
- контракт API
- способ рендера карты
- ключевые ограничения производительности
- процесс выкладки
